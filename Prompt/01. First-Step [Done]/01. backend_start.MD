Project: Sonatola Upazila Digital Platform — Backend Engineering

Act as a senior PHP backend engineer, database architect, API engineer, and application security engineer.

Build the backend for a digital public-service platform for Sonatola Upazila, Bogura, Bangladesh.

Mandatory technology constraints

- Plain PHP 8.x, using a version supported by the target hosting.
- MySQL or MariaDB with native SQL.
- PDO for all database access.
- HTML, CSS, and vanilla JavaScript may be used where needed.
- REST API with JSON responses.
- No Laravel, Symfony, CodeIgniter, or other PHP frameworks.
- Do not introduce Node.js as the backend.
- Design the backend to support a future Android app built with Capacitor.
- The public website must work without requiring visitors to register.

Your responsibility

You are responsible for implementing the project in the actual workspace, not merely explaining how to build it.

Phase 1: Inspect and plan

1. Inspect all existing project files before changing anything.
2. Identify the available PHP version, Composer availability, database requirements, and hosting constraints where discoverable.
3. Preserve useful existing files and avoid destructive changes.
4. Create a concise implementation plan and a clear project folder structure.
5. Write the architecture and development instructions in README.md.

Do not claim to have tested a database or environment unless you actually did so.

Phase 2: Database engineering

Create versioned SQL migrations and seed scripts for:

- Upazilas and unions
- Users and account status
- Roles, permissions, user-role assignments, and role-permission mappings
- News and categories
- Notices
- Service directory
- Citizen complaints
- Complaint assignments and status history
- Applications and application status history, with online applications disabled by default
- Media file metadata
- Notifications and device tokens
- Password reset and verification tokens
- Audit logs
- Application settings

Use InnoDB, utf8mb4, foreign keys, appropriate unique constraints, and indexes.

Include safe migration procedures, a schema documentation file, and a rollback strategy. Never execute destructive production migrations automatically.

Seed the initial location as Sonatola Upazila, Bogura District. Do not invent official union lists or administrative contact information. Provide a clearly documented method for importing verified official data.

Phase 3: Backend architecture

Create a maintainable structure with:

- A front controller and routing system
- Request and response handling
- Configuration management
- Database connection management
- Controllers, services, and repositories
- Request validation
- Authentication and authorization middleware
- Centralized exception handling
- Structured logging
- API versioning under /api/v1
- Database migrations and seeds
- Automated tests

Keep business logic out of route definitions and avoid duplicating logic between the website and API.

Phase 4: Authentication and permissions

Implement:

- Secure password hashing and verification
- Login and logout
- Session security for browser-based administration
- CSRF protection for state-changing browser requests
- Appropriate API authentication for future mobile clients
- Role-based access control
- Resource-level authorization
- Union-level and upazila-level data scoping
- Login throttling and account status checks
- Secure password reset and verification-token handling

Support the roles Super Admin, Upazila Admin, Union Admin, Editor, Service Officer, and Citizen.

Never rely on frontend controls alone for authorization. A union administrator must not access or modify another union's restricted records by changing an ID in the URL or request body.

Do not create a publicly accessible default administrator account or hardcode production credentials. Document a safe first-admin bootstrap process.

Phase 5: API implementation

Implement and document endpoints for:

- Public news, notices, union directory, and service directory
- Citizen registration and authentication
- Citizen profile
- Complaint submission
- Citizen-owned complaint tracking
- Authorized complaint assignment and status updates
- Administrative news and notice management
- User, role, and permission management
- Audit-log access for authorized administrators

Use consistent JSON response formats, correct HTTP status codes, pagination, filtering, input validation, and safe error messages.

Document each endpoint's method, URL, authentication requirements, permissions, request body, response body, and possible errors.

Phase 6: Security

Apply OWASP-aligned security practices:

- PDO prepared statements
- Context-appropriate output escaping
- CSRF protection where applicable
- Authentication and authorization checks on every protected endpoint
- Safe file uploads and private file storage
- MIME and file signature validation
- Request size limits and rate limiting
- Secure cookie configuration
- No secrets committed to version control
- No database credentials in public files
- Production error display disabled
- No sensitive personal data in application logs
- Restricted CORS configuration
- Secure backup and restore documentation

Keep private configuration, logs, backups, and uploaded citizen documents outside the public document root wherever possible.

Do not store OTPs or password-reset tokens in plaintext. Do not store passwords in plaintext.

Phase 7: Testing and verification

Create automated tests for:

- Database connectivity and migrations
- Authentication and session handling
- Invalid input
- SQL injection resistance
- Authorization and privilege escalation
- Cross-union data access
- Complaint submission and status history
- Public content visibility
- Unauthorized file access
- API response formats

Run all available tests and syntax checks. Fix failures and rerun the relevant tests.

If MySQL/MariaDB, credentials, or external services are unavailable, clearly identify the untested items instead of fabricating successful results.

Phase 8: Deployment readiness

Provide:

- .env.example with placeholders only
- .gitignore
- README.md
- Database installation and migration instructions
- Shared-hosting deployment instructions
- Production configuration checklist
- Backup and restoration instructions
- API documentation
- Test instructions
- A list of remaining limitations

Ensure the web server's document root points to the public directory. Provide appropriate Apache configuration where supported, but do not assume .htaccess works on every host.
